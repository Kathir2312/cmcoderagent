# Security scan: SAST and SCA, whole repository (7 October 2026)

Commit scanned: `8270028` (Phase 6 complete). Every finding below was looked at
in the code; "false positive" means checked and not exploitable.

**Summary: nothing critical or high reaches developers' PCs.** The only known
vulnerable packages are in build- or test-only dependencies that the shipped
files don't contain (checked inside the built `.vsix`). The actionable items are
hardening of the GitHub workflows (medium) and a few low-severity cleanups.

## Recommendations

| # | What | Severity | Effort |
|---|---|---|---|
| 1 | **Harden the workflows:** `permissions: contents: read` at the top of each (`contents: write` only for the release job); pin every action to a commit SHA (with its tag as a comment); no caches in `release.yml`; `persist-credentials: false` on checkouts | medium | small; CI reruns to prove it |
| 2 | **Drop the `chroma` extra:** run CI's test Chroma server from the `chromadb/chroma` Docker image instead, so `chromadb` leaves `uv.lock` and the four pip-audit waivers go | low | small |
| 3 | **Keep these scanners in CI:** Semgrep, gitleaks, zizmor and osv-scanner as a job in `ci.yml` (today's CI runs Bandit, pip-audit, npm audit and the OSV check of OpenJFX/NuGet) | — | small |
| 4 | **Chat panel:** accept `message` events only from the page itself or its host window | low | small |
| 5 | `usedforsecurity=False` on the SHA-1 fingerprints; `defusedxml` in `packaging/brand.py` | low | small |

## Resolved (7 October 2026, the same day)

All five recommendations were applied:

1. **Workflows:** every workflow starts with `permissions: contents: read`
   (only the release bundle job has `contents: write`); all 55 action
   references are pinned to commit SHAs (tag in a comment); the release build
   uses no caches (uv, npm and Maven caches off, the NetBeans download cache
   removed; the NetBeans zip is still checked against its SHA-512); every
   checkout has `persist-credentials: false`; a template expansion in a `run:`
   line goes through `env:`. zizmor: 94 findings → none.
2. **`chroma` extra removed:** CI's test Chroma server runs from the
   `chromadb/chroma:1.5.9` image (pinned by digest) as a service container;
   `chromadb` and its dependencies left `uv.lock` (377 → 198 lines in the
   export), and the four pip-audit waivers are gone (pip-audit `--strict`,
   no ignores).
3. **Scanners in CI:** the `security` job now also runs Semgrep (fails on
   error-level findings), gitleaks over the whole history, zizmor, and
   osv-scanner over every lock file and `pom.xml`, each at a pinned version.
   Accepted false positives are marked where they are: `nosemgrep` with the
   reason on the line above (the three Java process launches, two test/eval
   tools) and `.gitleaksignore` (the three made-up test keys).
4. **Chat panel:** `message` events are taken only from the page itself, a
   frame around it, or a window of the page's own origin (`fromHost` in
   `clients/web-panel/src/bridge.ts`); a frame inside the page, a window it
   opened and any other origin are ignored, with tests for each. (The first
   version, 2026-10-07, took only the page and its direct parent: VS Code
   sends from another frame of the webview, at the webview's own origin, so
   the VS Code chat heard nothing until 2026-10-08. The real-VS Code test now
   checks that the chat page gets VS Code's messages.)
5. **`defusedxml`** reads the branding SVG (`packaging/brand.py`, a build-time
   dependency); the SHA-1 fingerprints already pass `usedforsecurity=False`
   and stay SHA-1, since they name existing code-search indexes (a different
   hash would make every developer re-index). Semgrep's SHA-1 rule is
   warning-level, below the CI gate.
